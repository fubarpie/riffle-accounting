# ADR 0010: Reconciliation and the statement vault

- Status: Accepted
- Builds on: ADR 0004 (ledger and tenancy), ADR 0006 (access control), ADR 0009 (SimpleFIN import)

## Context

Phase 4 lets a bookkeeper prove that the books agree with a bank or card
statement, and keep that statement with the proof. The ledger is append-only
(ADR 0004), so reconciliation must not edit journal lines. Statements are
untrusted user uploads that contain financial data, so storage must be private,
tenant-scoped and safe against path tricks and active content.

Code: `packages/db/src/reconciliation/`, migration `0006_reconciliation.sql`,
`apps/api/src/routes/reconciliations.ts`, `apps/api/src/vault.ts`.

## Decisions

### Reconciliation links lines; it never changes them

A reconciliation belongs to one asset or liability account and one statement
period. `reconciliation_items` links it to existing `journal_lines`. Nothing in
this feature inserts or updates ledger rows.

- Status is `draft`, `completed` or `voided`. Transitions are
  `draft -> completed`, `draft -> voided` and `completed -> voided`; a database
  trigger enforces them. Statement facts (account, dates, balances) are
  immutable after creation.
- Only **live** lines (`live_journal_lines`: the current entry of a non-voided
  transaction) can be cleared, only from the same account, and only if dated on
  or before the statement end. Older uncleared lines are outstanding carry-overs
  and are offered as candidates.
- A line can be in at most one non-voided reconciliation (partial unique index
  on `reconciliation_items (business_id, line_id) WHERE voided_at IS NULL`).
  The API also checks first, to return a readable 409.
- One draft per account (partial unique index). The account row is locked
  (`FOR UPDATE`) while creating, completing or voiding, so these serialise.

### Balances and signs

Balances are signed `bigint` minor units in the business currency, as the
statement prints them. A ledger amount is debit-positive; the statement amount is
`amount * sign`, where assets/expenses are debit-normal (+1) and
liabilities/equity/income are credit-normal (-1); a contra account flips it. So a
credit card that owes money has a positive closing balance.

`difference = closing - (opening + cleared)`. Completion requires exactly 0.
Balances are capped at 10^15 minor units to stay far from overflow.

### Chain of statements

The first reconciliation of an account may state any opening balance (default 0).
Every later one must open at the closing balance of the latest completed one
(the field is optional and defaults to it; a different value is rejected with
422) and must end after it. Completion re-checks this under the account lock. A
completed reconciliation can only be voided newest-first, so the chain stays
consistent, and not while the books are locked through its statement end.

### Completed means frozen

Once completed, items cannot be added, removed or altered (trigger, enforced for
every role including the table owner). A trigger on `journal_entries` also
refuses a reversing entry (edit or void) for a transaction that has a line in a
completed reconciliation: void the reconciliation first. Voiding stamps
`voided_at` on its items, which releases the lines; the rows stay as history.
In a draft, if a cleared line's transaction is edited or voided, the item is
reported `stale`, and completion is refused until it is removed.

Reconciliations cannot be deleted (no `DELETE` grant plus trigger). Every action
writes an `audit_log` row in the same transaction: `reconciliation.create`,
`.items`, `.complete`, `.void`, `statement.upload`, `statement.delete`.

### Tenancy and roles

All three new tables carry `business_id`, composite foreign keys that include it,
and the same forced RLS policy as other tenant tables. Owner, admin and
bookkeeper can write; viewers can read and download and get 403 on writes.
Non-members and cross-business ids get 404, indistinguishable from "not found".
Authorisation happens before the request body is validated or an upload is read.

### The statement vault

`statement_documents` holds metadata; bytes live on disk under
`STATEMENT_STORAGE_DIR` (default `./data/statements`; compose mounts the
`riffle-statements` volume at `/data/statements`). File storage rather than
`bytea` keeps the database small and backups simple, at the cost of backing up
two things together.

- **The client controls nothing about the path.** The key is
  `<business uuid>/<document uuid>`, generated by the server, checked against a
  strict regex in both the database (`CHECK`) and `VaultStorage`, and the resolved
  path must stay inside the root. The client filename is sanitised (directory
  parts, control characters and quoting characters removed) and stored only for
  display. Files are created with `wx` (never overwrite), mode 0600, directories 0700.
- **Type comes from the bytes.** Allowed: PDF, PNG, JPEG, CSV. The declared
  `Content-Type` must be on the list *and* equal the type detected from magic
  bytes; otherwise 415. CSV has no signature, so it must be valid UTF-8 with no
  control characters and must not start with `<` (rejects HTML/SVG/XML).
  Stored `content_type` is the detected one.
- **Size** is capped by `MAX_UPLOAD_BYTES` (default 10 MiB) in the multipart
  parser, which stops reading at the limit (413). One file per request.
- **Downloads** go through the API only, are tenant-checked (the document must
  belong to that reconciliation and business), and are sent with
  `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`,
  `Content-Security-Policy: default-src 'none'; sandbox` and `Cache-Control: private, no-store`.
- **Deletion** is allowed only while the reconciliation is a draft (checked in
  the API and by trigger). The file is removed after the transaction commits, so
  a crash leaves an orphan file, never a row pointing at nothing. Uploads write
  the file first and remove it if the insert fails. SHA-256 is recorded.
  Documents can still be attached to a completed reconciliation (a late PDF) but
  not to a voided one.

## Consequences

- The web "reconcile" screen can be built on `GET /reconciliations/:rid`, which
  returns the summary, cleared lines, candidates and the suggested set.
- Orphan files (crash between commit and unlink) can accumulate; a sweeper is not
  written yet.
- No antivirus scanning, no encryption at rest (use volume or disk encryption),
  and no per-file quota beyond the size limit.
- The 55000 (object-not-in-prerequisite-state) error code from the new guard
  triggers is mapped to HTTP 409 by the API error handler.
- Voiding a completed reconciliation is blocked by a business lock date
  (`books_locked_through`) on its statement end; otherwise any writer role may void.
- Multi-currency is out of scope: one currency per business.
